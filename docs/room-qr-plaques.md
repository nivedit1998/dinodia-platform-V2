# Room QR/plaque contract v1

The new endpoints use `schemaVersion: dinodia.v1`, `contractVersion: 1`, current selected-Home account access and OWNER/PROPERTY_MANAGER authority. Company operations require an active CXO/SENIOR_OPERATIONS_MANAGER session and same-origin POST. The feature needs no online Hub; no room code grants access automatically.

GET `homes/{homeId}/room-qrs` returns `homeId`, current registered `address`, `rooms` (areaId/displayName/originalName/codeState/generation/canReveal/canRequestPlaque/openRequest) and `nextCursor:null`. This bounded library refuses Homes over 64 active Areas rather than silently omitting them. `ISSUED` means decrypt/context/hash checks pass; `RECOVERY_REQUIRED` includes legacy hash-only and corrupt credentials; `NOT_ISSUED` means no prior credential. No ordinary list/receipt returns a resolver reference or ciphertext.

POST `room-qrs/{areaId}/reveal`: strict `{expectedGeneration:positiveInteger}`; returns that exact current `reference`, generation and Home/Area IDs. Keep it transient. Black QR modules, white quiet zone, no external rendering service.

GET `room-plaque-requests`: 50 records with `nextCursor`; optional `after` UUID. POST body: `{contractVersion:1,items:[{areaId,kind:FIRST_ISSUE}|{areaId,kind:REPRINT,expectedGeneration}],notes,confirmRegisteredAddress:true}`; 1–64 distinct Areas, one plaque each, notes ≤1000. Requires Idempotency-Key (16–160 safe characters). The server snapshots/encrypts the Home address; staff production/print/dispatch recheck its fingerprint and original membership/authority generation. No alternate shipping address/payment/courier API.

Request receipt: `{schemaVersion,contractVersion,request:{id,reference,status,revision,createdAt,productionStartedAt,dispatchedAt,completedAt,cancelledAt,canCancel,notes,items}}`. Items identify exact Area, kind, current/snapshot label, generation and active status. GET staff queue additionally permits a status filter; detail adds Home/address/blockedReason.

POST customer `.../{requestId}/cancel`: strict `{expectedRevision}` plus Idempotency-Key. Customers may cancel only REQUESTED orders. Staff `.../{requestId}/transition`: strict `{action,expectedRevision}` plus Idempotency-Key, except CANCEL which requires `{action,expectedRevision,reason}`. Staff can cancel REQUESTED, IN_PRODUCTION or DISPATCHED orders even when fulfilment is held. The normalized 1–500-character reason, previous status and employee actor are audited atomically; reason is part of the idempotency digest. Do not enter personal data or QR references in the reason. The Portal explicitly warns that physical work/dispatched goods may exist and are not recalled. Cancellation is terminal, never a rewind: all production/dispatch timestamps and issued credentials remain intact. It closes the open-item reservations in the same transaction, so the current authorized homeowner/manager can request a replacement. Customer `canCancel` remains false after production starts. Normal lifecycle: REQUESTED→START_PRODUCTION→IN_PRODUCTION→DISPATCH→DISPATCHED→COMPLETE→COMPLETED. Starting production atomically issues never-issued credentials or reuses the exact existing credential. No implicit rotation/recovery, no grants. Cancellation/completion closes open-item reservations in the same transaction. No additional schema migration is required for this recovery path; the existing AuditEvent holds the reason.

POST staff `.../{requestId}/print`: strict `{expectedRevision}`. Only IN_PRODUCTION/DISPATCHED/COMPLETED; current Home authority/address, active Area and exact credential are checked. Returns requestReference and plaques (areaId/current+snapshot label/generation/locally generated PNG data URL). A print retry is read-only and reproduces the same token. Browser print-to-PDF is supported, not a remote fulfilment operation.

All responses/errors use no-store and the canonical native error adapter. 400 invalid strict input; 401 ended session; 403 forbidden role/origin; 404 inaccessible Home/Area/request; 409 duplicate open order/stale revision or generation/payload recovery/fulfilment hold; 429 account abuse limit; 503 missing secure configuration. Safe messages distinguish conflicts without leaking a QR. Fresh account/session/device/membership policy is rechecked inside the transaction, including before replay disclosure.

Database additions: two fulfilment tables, partial unique active credential per Area and open item per Area, additive readiness checksum/model-count entry. Preflight refuses existing duplicate active credentials. Legacy hash-only labels stay scan-valid but are never reverse-engineered or silently replaced. Forward recovery retains schema, credentials and orders; never restore an old Store/database over issued labels. Existing scan/email-verification/owner-approval endpoints and expiry rules are unchanged.

## Release and recovery

The parent is `b913ff2785da0abca1b860823353cb77f64568d1` on `feat/platform-universal-category-analytics-20261023`. This feature does not require a Hub release. The migration is `20261023210000_room_qr_plaques`; run the counts-only `docs/room-qr-plaques-preflight.sql` on the verified target before applying it. Require zero ambiguous active Areas and preserve a validated private database backup. Check that the existing Platform envelope key is configured without printing it. The same key must remain available to all compatible deployments.

The old app and existing Room QR scan/access routes remain supported. The new app displays a service-unavailable retry state when the new endpoints are absent. Deploy the migration and this Platform release before delivering the new iOS feature. Production preflight, migration/deployment and Apple delivery are separate release actions; local integration tests perform none of them.

**The parent Platform is not a ready-made rollback after this migration.** Its readiness allow-list does not know the extra migration/tables. Recover by retaining this compatible backend/schema and hiding the new entry points in a reviewed forward release, or by preparing a compatibility patch for the old line before deploying it. Preserve all issued credentials, encrypted payloads, orders, audits and idempotency records. Never drop the new tables, rotate plaques or restore an earlier database snapshot over new requests. A lost browser print can always be prepared again with the same authenticated credential.

Verification uses `test/room_qr_plaques.test.mjs` and the real loopback/Postgres workflow in `scripts/room_plaque_integration.mjs`, called by the maintained integration harness. `ROOM_PLAQUES_ONLY=1` skips later unrelated scenarios; omit it for the complete harness. Tests create only disposable synthetic accounts, Home/Areas and references. The full harness has an explicit local-target/egress guard. Never supply Production database or app endpoints to it.

`ROOM_QR_IOS_LIVE=1` additionally runs the actual iOS provider/model against this disposable server, including app submit → employee queue → production issue → same-session refresh/reveal. Supply the existing `DINODIA_IOS_ROOT`, `ROOM_QR_IOS_DERIVED_DATA` and `ROOM_QR_SIMULATOR_ID`. The app test uses an explicit loopback-only transport bridge. Its private synthetic fixture is removed after the test, and the harness requires one executed, passing test rather than accepting a skipped/empty selection. Default full integration does not launch Xcode.
